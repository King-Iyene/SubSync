# S0.1: Test harness and safety rails

Status: in progress (see the evidence section at the bottom, filled in at the end of the stage).

## Goal

A safe base to build and test on: one command that proves the build is healthy, a browser test that proves the demo tenant loads at phone, tablet and desktop widths, a demo login that cannot exist in production, a kill switch, default-off feature flags for anything new, and a progress file so a fresh session can resume.

## Decisions

- **Vitest for new tests, Node's built-in runner for the existing 283.** Rewriting working tests to change runner is risk with no customer value (brief: extend, do not rewrite). `npm run verify` runs both.
- **Playwright runs against `next dev` with `DEMO_MODE=true`.** `next start` runs with `NODE_ENV=production`, which now (correctly) switches the demo off.
- **Demo allowed only when** `DEMO_MODE=true` **and** neither `VERCEL_ENV` nor `NODE_ENV` is `production`. A previews build has `NODE_ENV=production`, so the demo is off there too.
- **Kill switch `APP_MODE=maintenance`:** stops all job queuing (webhooks, daily and 15-minute refresh, Sync now) and the worker, skips the cron emails, answers the app's sign-in and data calls with 503, and shows a "back shortly" screen. Install and uninstall bookkeeping keeps running on purpose, so an uninstall during maintenance still removes data.
- **New features are default off.** A guard test fails if anyone adds a feature name to the list without either adding it to the default-off set or to the reviewed baseline.

## Definitions

None added to `docs/METRICS.md` (no metric in this stage).

## Data sources

None. The demo tenant is seeded by `src/lib/demo/seed.ts` (fictional agency, 13 accounts).

## Edge cases

- Demo flag set to `"TRUE"`, `"1"` or `" true"` must not enable the demo (exact match only).
- Production detected by either variable alone.
- Maintenance must be exact (`maintenance`); any other value is normal operation.
- A job queued by mistake during maintenance must not be run (queue and worker both guarded).

## Acceptance criteria

1. `npm run verify` green (typecheck, lint with 0 errors, build, Node tests, Vitest).
2. `npm run e2e` green: the demo tenant loads at 390, 768 and 1440 px with no horizontal scroll, shows only fictional data, and the maintenance screen renders when the app is told it is down.
3. Tests prove the demo cannot be enabled in production, and that the kill switch blocks sign-in, queuing and the worker.
4. New-feature-default-off guard test exists.
5. `docs/PROGRESS.md` and `docs/FEATURE_STATUS.md` exist and are current.

## Incident during this stage

The first push failed to build on Vercel (the live site stayed on the last good deploy). Cause: Vitest was installed with `--legacy-peer-deps` to get past a peer conflict on `@types/node`, but Vercel installs without that flag. Local `npm run verify` could not catch it because the dependencies were already installed. Fix: upgrade `@types/node` to 24. Lesson for the runbook: add a clean-install check (`npm install --dry-run`) to the end of every stage that touches dependencies.
