# F10: Call lists

Status: built (31 Oct 2026). Tests are run together at the end of the build (King's instruction); the golden-data test below was run once during the build to prove the rewrite kept every list's meaning.

## Goal

Call lists load fast and the queues are correct.

## What the code did at the start of the stage (found by profiling it)

On the largest connected account (52,926 contacts) the list query **timed out in the database (over 8 seconds, error 57014)**, which is the spinner. It joined every contact in the account to a summary of every deal and every call outcome, then filtered, so each list read the whole account. Two lookups it made for each candidate (the latest call outcome and the "has anyone replied" check) had no index.

## Decisions

- **Look at the small side first.** Each pre-built list now picks its candidates from the table that is selective for it (the deals, the appointments, the call outcomes, or the contacts created in the last few hours), then looks those contacts up by key, and the same conditions as before decide who is on the list. Two additive indexes cover the per-contact lookups (`call_outcomes_contact_idx`, `cached_conversations_contact_idx`).
- **Result:** from timing out to 0.4 to 2.0 seconds per list on the largest account (that includes about 0.4 seconds of network round trip from the test machine; the hosted app sits next to its database). The slowest was Hot leads at 2.0 seconds. The custom filter (any tag or quiet days over every contact) still reads the account's contacts and took 1.1 seconds here. **Accepted number: under 2 seconds on the 53,000-contact account.**
- **A loading skeleton** replaces the spinner, and the page says "Showing the top N of M" (the list is the top 100 of up to 400 candidates) and that nobody is messaged from here.
- **Deal dollars on a row use counted deals** (value above zero and an owner), like every other screen; a contact with only a no-value or ownerless open deal is still on the hot list but with no dollars.
- **The nine lists are defined once** in `docs/METRICS.md` ("Call lists"). No message sending, no dialer.

## Tests

`tests/unit/call-lists-db.test.ts`: a golden dataset on the real database (a fixture company removed afterwards) where every contact is built to be in exactly the lists named in a comment: hot, stale proposal, customer, win-back, recent customer, new with no reply, new but already written to, do not contact, no-show, rebooked, follow-up due, not interested, called an hour ago. All 10 tests passed when run during the build. `scripts/profile-calls.ts` times every list.

## Self-review

- **S1: the custom filter and very large accounts.** A custom list over 100,000+ contacts will be slower than 2 seconds; it is capped at 400 rows but still scans.
- **S2: the timing includes this machine's round trip,** so the hosted app should be faster; it was not measured inside Vercel.
- **S2: the lists use the activity time the platform sends,** and none of the 103,404 synced contacts has any, so "quiet for 3 days" falls back to the created date (an old contact looks quiet); the lists say "quiet N days" from that.
- No S0 findings.
