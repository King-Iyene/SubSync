## 2. The five evaluation lines

- **(a) Decision and for whom.** The agency owner (and a business owner) decides what to fix first and whether the report is fit to put in front of a client. The client decides whether to act, which needs a next step. King decides whether this is worth $200: the report is the product's sales asset.
- **(b) Data truly available.** Nothing new is read: the numbers are the account totals (`accountRows`), the appointment view and the conversation window the other screens already use. Two list queries are new (stale deals, waiting conversations); they restate the same conditions as `accountRows` and a database test compares the totals (it passed once on the shared database, section 6). NOT VERIFIED on real data: a count against the CRM (King's check 2).
- **(c) Does the CRM already do it.** Its reports are per account and do not state a counting rule, keep counted money apart from estimates, or produce a client-ready fix plan across accounts. AgencyAnalytics-style reports are commodity; the audit's difference is the honest definition on every number and the fix plan.
- **(d) Simplest version that proves value.** No new table, no new route (the lists ride on the existing `audit` read), one self-contained report component with its own small stylesheet so it prints the same everywhere, wording and definitions as pure functions.
- **(e) Risk.** A public page: it holds only the snapshot, and the snapshot gains only wording, a brand name and a validated colour (tests prove no row field and no account name can enter). Money: the audit shows estimates, so each is labelled, ranged and never added to a fact. The shared `session.tsx` now sends the filter with the share request, so a link made while filtered covers only the accounts shown (the page says so).

## 4. What was built

- **One formula** (`followUpEstimate`, `metrics.ts`): the account tile (`derive.ts`) and the audit both call it. The estimate's range uses F1's `rateRange` on each account's won and lost deals, summed (`audit-intel.ts`). Below 20 closed deals: no figure and no range.
- **Definitions and windows** (`noteText`, `auditNotes`): each number has its definition in plain words with the settings used (stale days, reply target), and a window ("No change for 30 days or more", "Customer's last message more than 4 hours ago, within the last 30 days"). In the app a question mark beside each number shows it; on the shared page notes `[1]`, `[2]` ... point to a "How each number is counted" list. A test holds the stated windows to the appointment code (no-show 14 days, no outcome after 3 hours within 30 days) and to the conversation window.
- **What to fix first** (`fixFirstLine`): the most serious finding a person can act on, one sentence, at the top of the app page, the shared page and the pasted summary; none when nothing is urgent.
- **Lists behind the numbers** (KF-6, `audit-queries.ts`, router `computeAudit`): deals that stopped moving, waiting conversations, appointments with no outcome, no-shows not rebooked. They use exactly the audit's accounts (after the filter and the plan limit), never an id from the browser. The tile and each finding have "Show the N ...", opening the shared `DrillPanel` (new optional `backLabel`, "Back to the audit"), a name opens the lead panel, rows have "Open in your CRM".
- **Open buttons** say where they go ("Open in Pipeline and deals", "Open in Unanswered messages"...); a test holds the labels to the menu's own words. The shell's Back link and the browser Back button return to the audit (D0).
- **Page filter**: the audit read carries it already; `audit/share` now carries it too. The app says how many accounts the filter leaves out and that a link made now covers only the accounts shown.
- **Brand and print** (N85): the printed in-app page opens with the sender's name, colour rule and date; for print the dark shell's colours are replaced by the light theme's (`src/lib/design/print.ts`, held equal to `globals.css` by a test); the sender's colour is nudged only as far as it needs to read on white. The shared page carries the same name and colour. No logo: the app stores no logo (SKIPPED).
- **Shared report** (`src/app/audit/[id]/report.tsx`, a plain component with its own stylesheet): sender and date, what to fix first, the counted figure and the estimate in separate labelled cards (with the estimate's range and the one-deal outlier note), what we found, a numbered fix plan (start today, this week), a next step, how each number is counted, the counting rules' date, a print button. A sender with their own business name carries only their brand (no product sign-up link); an unbranded or older link keeps the old behaviour. Hardening is unchanged (token, 14 days, revoke, views, rate limit, noindex, generic previews, no referrer, print on A4 and Letter).
- **Snapshot** (`share-intel.ts`): every new field is optional (old links and the sample still read); colour must be six-digit hex; findings keep titles, fix steps and windows only; names are scrubbed from every field including the definitions.
- **Small server guard**: creating a link is refused for a client's staff in the handler too (not only the route table).
- **Sample audit script** builds the sample with the same functions a real link uses.

# First pass (31 Oct 2026), kept for history


Status: built and verified (31 Oct 2026). Evidence at the bottom.

## Goal

The audit is correct, sales-ready, and the public link is safe.

## What the code did at the start of the stage (found by reading it)

1. The audit's numbers come from the same counted deals, appointment rules and speed rules as F1 to F3 (one definition each), with counted facts and estimates labelled apart. Nothing to rebuild there.
2. The share link: a 192-bit random token (good), noindex (good), no account names (good), but it lived for 30 days, could not be switched off, had no view count, no rate limit, no link-preview tags (so a chat app could preview whatever the page title said), a dark page that printed as white text on a white sheet, and no fix plan.

## Decisions

- **Token:** unchanged, 24 random bytes (192 bits), unguessable by design.
- **Expiry:** 14 days by default (was 30), shown on the page and in the app.
- **Switch off:** the owner can revoke any of their links from the audit screen; only the owning installation can (another company, a client's own staff and a made-up id all fail), the action is written to the audit log, and a switched-off link shows nothing.
- **View count:** each open of a valid link adds one view and a last-opened time, shown in "Your share links".
- **Rate limit:** 30 lookups a minute per address on the public page, refused before the database is touched.
- **Previews:** the page sets generic title and description for link previews (no name), noindex, no archive, no snippet, and no referrer.
- **Snapshot date and expiry** are on the page; the fix plan ("What we found" then "One-page fix plan", five steps with what to do) is on the public page and printed with the in-app audit.
- **Print:** the public page prints with a white background and dark text on A4 and Letter, the sign-up button is not printed, and an item is never split over two pages.
- **Demo:** the demo installation holds the public sample audit, so its links are never listed or switched off from the demo.

## Acceptance criteria

1. Link security tests pass (expiry, view count, revoke by owner only, no names, noindex, previews, rate limit).
2. The public page is checked logged out and cannot reach any other data.
3. The print layout is checked on A4 and Letter.
4. `npm run verify` green.

### A bug the tests found

The public page read the clock before touching the database, which this project's rendering mode treats as an error ("blocking prerender current time"). The page worked, but it made the dev server unstable and the tenancy run failed with "fetch failed". Fixed with `connection()` before the clock read. Separately, my first rate-limit check built the link from `NEXT_PUBLIC_APP_URL` (localhost:3000 on this machine), not the test server.

### Self-review (S0 blocks release, S1 fix before pilot, S2 fix soon, S3 note)

- **S1: the rate limit is per server instance.** On Vercel two requests can reach two instances, so the real limit is looser than 30 a minute. The 192-bit token is what makes guessing impossible; the limit only makes it cheaper to refuse.
- **S2: the view count counts every open of the link, including your own and any chat-app preview robot that does not respect noindex.** It is a count of opens, not of people.
- **S2: a page cannot be proven to be absent from a search engine,** only that it asks not to be there (noindex, noarchive, nosnippet).
- **S3: PDFs were generated by the browser's print engine; a human should look at one printed copy** (check 4 below).
- No S0 findings.
