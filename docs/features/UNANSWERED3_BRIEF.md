## King's rules (non-negotiable)
- Money first: every feature must be something an agency or business owner pays for or a pain they feel daily. Best-of-best quality, be fast. While building, if you see a better or extra pain-point feature that fits the module, add it (small, flagged) and list it in your report.
- UI: simple, classy, sci-fi (glow, animated counters, replayable timeline like Speed's journey), little text (explanations in hover tips), cards named as the question they answer, a fold of 3 cards with the rest behind More. Light AND dark both right. Phone 390, tablet 768, desktop 1440, no sideways scroll, tap targets 44px on phone. Every count of people is clickable and opens exactly those people (count equals rows). Clicking a person row opens the full lead panel (not just a reply link).
- Scale: millions of conversations, 100 to 200 client accounts. SQL aggregates only, server-paged lists (20/50/100), never load all rows. DB is only 500 MB: tiny fixtures only, prefix ids with xtest-, always clean up. 100 CRM API requests per 10 s per location.
- Safety: all CRM writes ONLY through the safe write gateway (preview first, typed confirmation for delete, dry-run unless WRITE_GHL_LIVE and the account opt-in; audit log; DND, active-payment, open-deal and upcoming-appointment contacts protected from delete). All sends only through gated transports. Never turn on a live switch. Never write to a real client account. Writes SubSync makes must be excluded from our own reply metrics (rule 14).
- Tenant isolation is the top rule: derive company and location from the verified session, never trust ids from the browser; register new tables in src/lib/tenant-tables.ts and data-inventory.ts; add this slice's read addresses to scripts/check-tenancy.ts (append only). A client's staff see only their own account.
- White-label safe: never show vendor words (GoHighLevel, HighLevel, GHL, sub-account) in any UI text, email or error; use the white-label link helper for CRM links. Plain words, no jargon.
- Every feature behind its own flag in src/lib/flags-core.ts (default off) and entitlements. Additive idempotent migrations only (new file supabase/migrations/2026112x...sql). Do NOT apply migrations; the lead applies them. Never create or run big fixtures.
- Every metric gets a written definition in docs/METRICS.md and a unit test. Estimates are labelled estimates with the formula one tap away and "not enough data" under the minimum (about 30 closed deals or 100 leads).
- Tests: unit tests (node --test src/lib/__tests__/ style and tests/unit), DB tests written but only run if the migration is already applied (skip otherwise), Playwright specs for the new screens at 3 widths written and run once at the end for your slice, one width at a time.

## Process rules
- Work only in your own worktree and branch (given in your slice), cut from branch stage/unanswered3. Create the worktree with `git worktree add C:\Users\KING\wt\<NAME> -b <branch> stage/unanswered3`, junction node_modules from the main repo, copy .env.local, set a local-only turbopack root in next.config.ts and mark it skip-worktree. Use your own dev port.
- NEVER run check-tenancy. NEVER push to main. NEVER apply migrations. Push only your branch. Use `git add <named files>`, never -A. Commit small and often.
- After each feature run: `npx next typegen && npx tsc --noEmit` and `node --test src/lib/__tests__/` and the unit tests you touched. Fix before moving on.
- If a tool call fails with a permission or classifier error: retry once, then skip, note it in your report, and continue.
- Do not create scheduled tasks. Be token-lean in your final report: under 200 words: branch, head sha, features done, features not done and why, migration filename(s), flags added, new read addresses for check-tenancy, anything for the lead to merge carefully.
