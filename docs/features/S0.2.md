# S0.2: Identity, roles and tenant isolation

Status: PASSED by King (31 Oct 2026). Evidence is at the bottom.

## Goal

No one ever sees data they should not see, and nothing a tenant gave us survives its uninstall.

## What the code did at the start of the stage (found by reading it)

1. The SSO parser (`src/lib/ghl/sso.ts`) kept `role` and `type` but **dropped `isAgencyOwner`**.
2. `decideAccess` (`src/lib/access.ts`) **ignored the role for agency users**: any agency user, including a staff member with role "user", got the agency view of every client account. Brief 4.1 says staff see only the accounts they can access, and nothing if that cannot be verified.
3. A client-account user with role "user" got the same business view as the account's admin (including Settings). Brief 4.1 says an account user sees only their own account, with no settings or plan information.
4. `purgeInstallation`, `purgeSyncedData` and `purgeLocationData` list tables by hand. Twelve tables that hold tenant data were missing, among them meeting notes, connection tokens, API keys, cleanup snapshots, reply-speed rows and shared audit links.
5. Log lines print `error.message`. A database error message can contain row values (for example "Key (email)=(a@b.c) already exists").

## Decisions

- **One identity function, `deriveIdentity(payload)`** in `src/lib/identity.ts`. Input: the decrypted SSO payload only. Output: `{ userId, companyId, activeLocation, userType, role, isAgencyOwner }` where `role` is one of `agency_owner`, `agency_admin`, `agency_staff`, `account_admin`, `account_user`. Strict: `isAgencyOwner` counts only when it is the boolean `true` (a string "true" does not). A missing or unknown role is treated as the **least** privileged role of that user type.
- **Role rules (CLAUDE.md 4.1):**
  - agency owner or admin: the agency view (as today).
  - **agency staff: refused**, with a clear message, until access can be verified through the Users API (a CHECK item in the brief). Default deny.
  - account admin: their own account, all views and settings (as today).
  - **account user: their own account, read-only, no settings or plan pages** (the existing "client" kind), even when their business installed the app.
- **Identity log:** each sign-in writes one row to a new additive table `identity_log` (role, user type, isAgencyOwner, whether a location was present, outcome). No names, no emails, no ids of people. This also answers CLAUDE.md checklist item 12 (real payload shapes).
- **One list of tenant tables,** `src/lib/tenant-tables.ts`, drives all three purge functions. A test compares it with the database schema, so adding a table without classifying it fails the build. Kept on uninstall on purpose: `audit_log` (the minimal audit record the brief asks for), `install_plans` (billing record, no customer data), and the installation row itself with its tokens emptied.
- **Route registry,** `src/lib/route-guards.ts`: every API route file and page route, with its guard. A test walks the source tree and fails for any route not in the registry. `docs/TENANCY.md` documents the same table.
- **Safe logging:** `src/lib/safe-log.ts` redacts key-value fragments and long token-like strings from any message before it is logged; all 22 log sites use it.
- **Secrets:** a script searches the built front-end files for the value of every server-side secret (the values are read from `.env.local` and never printed), and a value-based search runs over the full git history. gitleaks is not installed; downloading it needs King's yes (see evidence).

## Definitions

None added to `docs/METRICS.md` (no metric in this stage).

## Edge cases

- `isAgencyOwner` as string, number, null or missing.
- Role in a different case ("Admin"), with spaces, or missing.
- Agency payload without a company id; account payload without an active location.
- An agency user with an active location whose business installed the app themselves.
- An account user whose agency switched client view on versus a business that installed itself.
- A payload encrypted with the wrong key; a payload that decrypts to non-JSON.
- A forged session token; a session for company A used with ids of company B.
- Uninstall while the kill switch is on (must still delete data).

## Acceptance criteria

1. `deriveIdentity` and the role rules have unit tests for all five roles and the edge cases above.
2. The real sign-in route is tested end to end with fixtures: owner and admin in, staff out, account admin in, account user read-only, wrong key refused, uninstalled company refused.
3. Tenant isolation: the existing two-agency attack suite still passes, plus attacks as an account user, plus the share link and the webhook endpoint.
4. Uninstall purges every table in `tenant-tables.ts` except the documented keeps; a schema-drift test proves the list is complete.
5. `docs/TENANCY.md` lists every route and its guard; a test proves no route is missing.
6. Token encryption at rest, refresh rotation lock, no secrets in the built bundle, and safe logging are each verified with a test or a script.
7. `npm run verify` and `npm run e2e` green.

# Evidence (31 Oct 2026)

## What changed

- **Identity:** `src/lib/identity.ts` (`deriveIdentity`, five roles) and `decideForIdentity` in `src/lib/access.ts`. `/api/sso` now derives the role from the verified payload only, refuses an unreadable payload (403), refuses agency staff (default deny), and gives an account user the read-only client session.
- **Identity log:** table `identity_log` (migration `20261031150000_identity_log.sql`, applied). One row per sign-in: role, user type, isAgencyOwner, location present, outcome. No names, emails or person ids.
- **Uninstall completeness:** `src/lib/tenant-tables.ts` is the one list. Twelve tables that held tenant data were missing from the old hand-written purge lists (meeting notes, connections, API keys, cleanup snapshots and others). All three purge functions now read the list.
- **Route guards:** `src/lib/route-guards.ts` plus `docs/TENANCY.md` (every route and its guard).
- **Safe logging:** `src/lib/safe-log.ts`, used at every log site that printed an error message.
- **Secret scans:** `scripts/check-bundle.mjs` (chained into `npm run verify`) and `scripts/check-history.mjs` (`npm run check:history`).
- **Help page:** the FAQ "How do I remove SubSync and my data?" now says exactly what is deleted and what is kept.

## Self-review (S0 blocks release, S1 fix before pilot, S2 fix soon, S3 note)

- **S1: staff default-deny is a behavior change for real agencies.** Agency staff who could open the agency view before are now refused until the Users API check exists. Safe (default deny), but a pilot agency with staff will ask. The refusal message tells them to ask the agency owner.
- **S1: King's own real role is unconfirmed.** No real payload has been logged yet (the log table is new). If King's account were sent as agency with role "user" and isAgencyOwner false, they would be refused. Check 1 below proves it live. Rollback is one revert of `src/app/api/sso/route.ts`.
- **S2: unknown share ids return HTTP 200 with not-found content** (Next.js cache components do not give a real 404 inside Suspense). Nothing leaks; search engines may index junk. Fix with F6.
- **S2: no way to revoke a share link until F6.**
- **S2: refresh-token rotation is compare-and-swap, not a lock.** Two parallel refreshes cannot both win, the loser retries with the saved token; proven by test, not by a load test.
- **S2: gitleaks is not installed.** The value search plus shape search is a stand-in. Downloading gitleaks needs King's yes.
- **S2: tests share the production Supabase project** (fixtures use `xtest-` ids and clean up after themselves; two test rows in `identity_log` have no installation).
- **S3:** the repo sits in OneDrive and `.next` locks need `rm -rf .next` between runs.
- No S0 findings.
